# 0.0.3 Implementation Plan — Presentation, Tome Cleanup and Storage Limits

**Goal:** Deliver the ten requested 0.0.3 improvements: storage and quartz rendering, Manifest XMI support, configurable placement limits, readable block previews and streamlined Tome navigation, consistent unfinished-content hiding, default-on Arcane Arsenal, and lectern-anchored solid locator beams.

**Architecture:** Keep shared gameplay in the existing Java source tree and isolate only actual loader/version APIs. Reuse existing block-entity synchronization, optional viewer callbacks and SavedData patterns. No new dependencies or general-purpose framework is planned.

**Tech stack:** Existing Stonecutter layout; Minecraft 1.20.1 Fabric/Forge and 1.21.1 Fabric/NeoForge; Java 17/21; existing optional EMI/JEI integrations.

**Execution:** Planning only. Implement directly, without coding delegation. No authorization to commit, push, publish or change versions immediately. This plan is the only project file written during planning.

## Decisions and remaining approval

User-confirmed release scope:

1. Radiant Chest stack numbers must appear like a vanilla chest, in front of the item rather than behind it.
2. Quartz growth must be displayed through a block entity renderer.
3. Manifest must support EMI as well as JEI; the UI name is exactly **XMI integration**. Prefer EMI when available, otherwise JEI.
4. Render one item above each occupied stored ingredient slot in the Radiant Crafting Table model, independent of the stack count.
5. Independent limits of **64 chests, 64 troves, and 64 tanks per player across all dimensions**, configurable on the server.
6. Replace the Tome's small item representation on block presentation pages with a proper block display. This interprets the user's report as a presentation defect; recipe ingredient icons remain ordinary item icons.
7. Keep only **Blocks**, **Items** and **Concepts** sections in the Tome. Remove redundant home/index/table-of-contents sections; redistribute useful gem entries rather than deleting finished content.
8. Hide all unfinished content from the Tome, creative tab and EMI/JEI.
9. Enable **Arcane Arsenal by default**, retaining an explicit configuration opt-out.
10. Lectern-origin tracking must draw from the lectern, not the player. Replace pixel-width lines with attractive solid square-section beams approximately **1/16 block thick**. “Cubic line” is interpreted as volumetric rectangular-prism geometry, not a cubic Bézier curve.

There is no existing placed storage to migrate. Do not build a legacy-storage migration or discovery/backfill project.

Interpretation: quartz growth means the growing raw quartz above the Radiant Resonator; the renderer belongs to its existing block entity, not to a newly invented ticking quartz block.

Confirmed placement policy (supersedes the initial recommendations):

- `0` = unlimited; positive values = maximum; default 64 for each type. Do not implement a special “disable all placement” mode or a negative unlimited sentinel. Reject negative values without overwriting the config.
- Creative players bypass quota enforcement. Still account for their successful owned placements, so switching to survival checks the actual total including creative placements. No mode-change handler, retroactive removal, disabling of storage or excess-quota remediation is needed.
- Survival players at or above a positive limit cannot place another block of that type, including after returning from creative. Existing blocks remain usable; quota enforcement acts only on new placements/conversions.
- Resolve fake-player, no-player and command placement policy from the existing ownership/placement contract; do not silently assign another player's ownership from item data. Ask only if that contract does not determine the new quota behavior.

## Inspected baseline and evidence

Paths below use `J = src/main/java/com/aranaira/arcanearchives`.

- `J/client/RadiantChestScreen.java:107–114` draws custom full counts with `renderItemDecorations` inside `renderLabels`; the rest of rendering delegates to the native container screen. The layering root cause is a hypothesis until native slot render order/depth is inspected and reproduced.
- `J/tileentities/RadiantResonatorBlockEntity.java:68–107` owns server growth, online gating, obstruction checks, completion and updates every 50 ticks or status change. It already sends `current_tick`/`can_tick` update state. `progressPercentage()` uses local `ServerSideConfig`, so a renderer must not assume remote clients share the server's configured duration.
- `J/tileentities/RadiantCraftingTableBlockEntity.java` persists nine real inputs and three recipe bookmarks, but has no explicit update packet/tag implementation. `J/inventory/RadiantCraftingMenu.java` calls `table.setChanged()` in its mutation paths. Disk persistence alone does not provide nearby observers with rendering state.
- `J/integration/emi/ArcaneArchivesEmi.java` already registers recipe display/crafting transfer; Manifest search binding is absent there.
- `J/client/ManifestSearch.java` has one callback binding and captures its identity for a screen session. `docs/behavior-changes/0134-manifest-search-integration.md` documents existing JEI query copy/sync/conditional restoration. Preserve these semantics for either provider.
- `J/config/ServerSideConfig.java` loads `config/arcanearchives/server.properties`, preserves existing files and rejects malformed values without overwriting them. It currently has a resonator limit, not storage-placement limits.
- `J/data/ResonatorSaveData.java` demonstrates persisted dimension/position ownership accounting that survives chunk unload without force-loading. Storage quotas should reuse that pattern where appropriate, not the loaded-only discovery view.

- `J/client/ManifestRayRenderer.java:48–49` unconditionally chooses the player position plus one block as origin. It draws `DEBUG_LINES` and calls the pixel-width function in `J/client/ManifestRays.java`; lectern origin is not selected there.
- Tome resources under `src/main/resources/assets/arcanearchives/patchouli_books/tome_arcana/en_us/categories/` include `blocks`, `items`, `concepts`, `gems`, `home`, `index` and `tableofcontents`. The Radiant Chest entry references converted presentation templates.
- `J/integration/ViewerHiddenItems.java` currently hides chromatic powders and, when Arsenal is disabled, its gem list; it is not a comprehensive unfinished-content policy. `J/integration/patchouli/TomeConditions.java` exposes Arsenal/integration flags; creative output in `J/init/ContentRegistry.java` also checks Arsenal separately.
- `J/config/ArsenalConfig.java` currently initializes Arsenal false, writes `EnableArsenal=false`, and defaults absent boolean keys to false. Changing only generated-file defaults would miss startup and missing-key behavior.

These are source observations, not fresh build or runtime acceptance results. The follow-up planning inspection found only the existing untracked `.hermes/` plan directory on `main`.
