# 0140 — Manifest tracking after access revocation

Status: approved by the user's explicit “yes” to removing already-selected tracking markers after losing Hive access, even while the Manifest is closed. Server selection state, C2S commands, Hive-grant pruning and S2C tracking synchronization are implemented. Native codec/receiver/server-path checks pass; rendered markers and connected end-to-end acceptance remain pending.

## Original behavior

At pinned upstream `bb99accf48ed583e29b0efae56e28c963407b8df`, `util/ManifestTrackingUtils.java:37–58` copies a selected entry's item/location references into a client-side per-dimension map. `client/render/LineHandler.java:26–30` draws those cached positions in the current dimension without consulting current Hive visibility.

The traced removal callers are explicit tracking clear/remove actions, login clearing, and `GUIRadiantChest.java:715–718` removing a visited chest. The tracked-coordinate renderer does not itself revalidate membership. This describes previously received information, not a mechanism for querying new unauthorized inventory contents.

## Approved behavior

Stop displaying a tracked source when the server determines that the viewer no longer has personal/Hive visibility, including while the Manifest screen is closed. Preserve ordinary explicit selection/clearing and dimension-specific rendering. Do not force-load chunks, add remote extraction, or send inaccessible inventory contents.

## Reason and decision

The 0.0.2 plan requires tracking without exposing inaccessible storage, while upstream renders previously cached locations. The user approved applying current access rights to already-selected markers as well as new listings. Clearing previously selected markers is an explicitly approved observable change.

Decision: remove markers after server-authoritative access revocation. Retaining cached historical markers after access is lost was not selected.

## Affected targets

Minecraft 1.20.1 Fabric/Forge and 1.21.1 Fabric/NeoForge.
