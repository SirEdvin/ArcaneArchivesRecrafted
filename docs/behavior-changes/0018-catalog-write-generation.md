# 0018 — Catalog write generation at input commit

Status: implemented under the user's delegated behavior-change authority; runtime integration remains pending.

Upstream baseline: `80944ce45c6559243d8928cc4b305bf379388652`, `recipe/gct/GCTRecipeList.java:104-124`: add/remove update the map and invalidate cached lists. There is no transaction-generation guard upstream. The port's 0017 guard compared recipe identity before/after callbacks; removing and restoring the same object defeats that guard. This is a reproduced port boundary defect, not evidence of a legacy multiplayer exploit.

Decision: assign a fresh private generation token after every accepted catalog write, including same-object replacement and removal of a missing name. Input consumption captures the token and requires it unchanged before and after each condition callback. This rejects remove/re-add and replace/restore sequences during matching or condition evaluation. Any intervening catalog write, even unrelated to this recipe, conservatively cancels this attempt; a later attempt can resolve the new catalog. Invalid writes rejected before mutation do not invalidate the token. No callbacks run between map mutation and token replacement; ownership remains single-server-thread, not a concurrency guarantee.

Rationale: recipe identity alone does not establish an unchanged catalog. An opaque token avoids counter wraparound without new dependencies or per-recipe bookkeeping. Alternatives: retain identity-only checks (misses ABA), per-name revisions (unneeded complexity), or ban all Java callbacks (breaks existing extension boundary). Callback side effects are not rolled back; conditions must still be effect-free reads of authoritative server state.
